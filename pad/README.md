# Pad: Uniswap v4 launchpad on Robinhood Chain (quote token = $STAG)

Status: audited internally in repeated hostile rounds; NOT yet deployed; needs lawyer sign-off on the holder payout (peace mode) before mainnet.

## What it does
- `PadFactory.launch` makes a token, opens a $STAG / token v4 pool with `PadHook` attached and seeds the whole 1B supply as one-sided liquidity the factory owns and can never remove. The creator collects the pool's LP fee (0.30%). No launch minimum, no bonding curve. Minimum starting value is 1,000,000 $STAG.
- `PadHook` takes 3% of the $STAG leg of every swap. Buy tax: **war mode** -> the project's war chest; **peace mode** -> 1/3 creator, 2/3 holders (paid in $STAG through the token's dividend counter). Sell tax -> platform. The hook keeps everything as ERC-6909 claims at the PoolManager.
- A war chest can only buy the project's own token through its own pool and burn it. The creator burns whenever they like, at most one burn per pool per hour, each call limited to ~1.5% price impact.
- `PadBattle`: a creator challenges another project (their own pool locks while the offer is open), the opponent accepts, both pools lock, the clock runs. Higher $STAG volume since acceptance wins. Only what each pool earned DURING the fight is at stake: the loser's fight earnings move into the winner's chest, and the winner's fight earnings plus that loot are marked "forced" and get burned (creator first; strangers may burn it in steps). Older chest money stays with its pool. Ties move nothing.

## Rules worth knowing
- Where the $STAG side of a swap is specified, the swap must fill completely or it reverts (so tax and volume are always on what really traded). Swaps that fill nothing revert.
- Only the factory can add liquidity to a pool. Zero-liquidity pokes (fee collection) are allowed.
- Dividends are staged and credited at the first token interaction of a later block, so tokens borrowed for one transaction never earn.
- Hook owner powers: take the platform's sell-side share, hand ownership over in two steps, wire the factory and battle once.
- Names/symbols: letters, digits, space and `. _ - + ! ? : #` only. The site must still trim, collapse whitespace and flag duplicates/look-alikes.

## Known limits (accepted, documented)
- **Wash trading** can win battles; it costs the trader tax and fills chests.
- **One person can run both sides of a battle** and move the loser's fight earnings into the winner's chest. A creator already controls their own chest (they can choose never to burn it), so this adds no power over honest buyers; in audits it lost money in every measured case (burn cap 1.5%/hour, 3% sell tax). It cannot be prevented by any rule (second wallet).
- **A loser can try to force an exact tie** by topping up volume in the last second; a tie moves nothing.
- **A pool pumped to the top of its range** has nothing left to buy: burns revert, a forced chest then stays stuck and that creator cannot start the next fight until it can be burned.
- **`block.number` on this chain is the Ethereum (L1) block number** (Arbitrum-style): "a later block" for dividend crediting means a later L1 block, ~12 s, spanning many chain blocks. This is stricter than intended and flash-take protection still holds.
- Parked dividends (eligible supply under 1 token) go to whoever first holds a token across the next block boundary.
- Exact-in and exact-out trades differ by ~3% in effective tax; volume is the pool's actual $STAG leg.
- Third parties can create their own hook-less pool for the same token; it is outside this system.
- Starting price snaps to the pool's 60-tick grid in the creator's favour: the real start is at or slightly above the request (up to ~0.6%). In the token-is-currency0 ordering an adversarially chosen request can land up to 1 wei of STAG below it (integer square-root rounding); this cannot undercut the 1,000,000 STAG minimum.
- The PoolManager's owner can set a protocol fee (at most 0.1%) on any pool, pad pools included; it would slightly reduce creators' LP fees and has no effect on solvency.
- Aggregators that price from a pool's raw price alone will miss the 3% tax; quoters that simulate the hook price it correctly.
- Routers: standard v4 routers work; a router that syncs $STAG before the swap works (the holder flush steps aside).

## Mainnet deployment (see scripts/)
Rules of the road: never announce an address or send anyone to the pad until the FINAL readback (after the multisig accepts, with `EXPECT_OWNER_ACCEPTED=1`) passes. Note `factory.launch` is permissionless the moment the deployer lands, so third parties can launch before you do; that is harmless to the system but means "nothing has launched" is not guaranteed. The deployer key is a throwaway: fund it only for gas and discard it afterwards.

**Trust anchors you must obtain out of band** (the scripts cannot supply these): (a) the audited commit hash and the keccak digest of `audited-manifest.json` published with the audit report (`EXPECT_MANIFEST_DIGEST`; at the time of writing `0xca4321cc7077227dc7343a55106a19f0dfde057670594afbf14abbacaaf7ec5a`, but trust the published report, not this file); (b) the multisig address compared in the Safe app by the signers themselves (the scripts cannot prove the address is the one you intend: a look-alike contract is stopped only by the code-hash check below and by this human comparison), its owner list (`EXPECT_OWNERS`), threshold (`EXPECT_THRESHOLD`), the Safe implementation address (`EXPECT_SINGLETON`, from Safe's published deployments), the canonical SafeProxy runtime code hash (`EXPECT_PROXY_CODEHASH`, e.g. `cast keccak $(cast code <a proxy you created through the official Safe factory>)`, cross-checked against Safe's deployments repo), and the handler pair `EXPECT_FALLBACK` + `EXPECT_FALLBACK_CODEHASH` (only if the Safe has a fallback handler; it must be the official CompatibilityFallbackHandler: the scripts also refuse any handler that is one of this system's contracts, PM, STAG, the Safe itself or the deployer EOA, because the Safe forwards any unknown call to it as itself. Never copy the handler the script prints into the pin to make a row pass). Also pin the code, not just the addresses: `EXPECT_SINGLETON_CODEHASH` and `EXPECT_FACTORY_CODEHASH` (`cast keccak $(cast code <addr>)`, cross-checked against Safe's published deployments on a second machine). (c) the Safe's creation transaction hash (`EXPECT_SAFE_CREATION_TX`) and the official SafeProxyFactory address (`EXPECT_SAFE_FACTORY`, from Safe's published deployments): the scripts require that transaction to be sent TO that factory, that the factory logged exactly one `ProxyCreation` for the multisig with the pinned singleton (so only the factory's own CREATE2 of the canonical proxy code could have made it: no hostile constructor and no forged log), that exactly one `SafeSetup` from the multisig was logged before it with `initializer == 0` (so `setup()` made no delegatecall that could plant unlisted owners/modules or pre-approved hashes), and owners/threshold unchanged since. Create the Safe with `to = 0x0` in its setup (the plain `createProxyWithNonce` path; Safe app flows that use a `SafeToL2Setup` initializer will deliberately fail this check) and use a fresh Safe made for this purpose. (d) Compare the PoolManager and STAG addresses in `scripts/lib.js` with official sources and the STAG symbol/decimals on the explorer.

## Tests
`RH_BLOCK=<near head> npx hardhat test` (mainnet fork). `npx hardhat --config hardhat.nolimit.config.js test test/deploy.dryrun.test.js` for the deployment dry run.

RPC independence cannot be enforced by a script (the script only checks that the host names differ): choose two genuinely separate providers, ideally one your own node. The solvency scan is bounded (`SCAN_MAX`, default 300, a positive integer); see below if launches exceed it.

Residual co-signer risk (no script can remove it): any owner of the Safe can `approveHash` for future nonces, owners can be contracts that sign without a key, and the signers collectively control the Safe. Use only signers you trust, hardware keys, and a threshold of at least 2. `deploy.js` checks the Safe on one RPC only (the default public one unless `RH_RPC` is set); the dual-RPC readback before `acceptOwner` is the real gate. Use `https` RPC URLs.

**Creating the Safe** (plain path, `to = 0x0`): call the official SafeProxyFactory's `createProxyWithNonce(singleton, setupData, saltNonce)` directly (for example with `cast send`), where `setupData = setup(owners, threshold, address(0), 0x, fallbackHandler, address(0), 0, address(0))` and `fallbackHandler` is `0` or the official CompatibilityFallbackHandler. Safes made through the Safe app use a `SafeToL2Setup` initializer, so they fail the strict checks on purpose. `EXPECT_PROXY_CODEHASH` is the keccak of the runtime code of a proxy made by that same factory (any proxy it created has the same code). Check whether the Safe app/transaction service supports chain 4663 before you rely on it; if not, collect signatures with `approveHash` or offline EIP-712 signatures through a script, and rehearse that path.

**Rehearsal and the accept transaction**: every owner must prove a key by calling `approveHash` on-chain for the rehearsal Safe transaction (the Safe only validates the first `threshold` signatures, so a transaction that merely carries all signatures does not prove every owner can sign); alternatively run enough rehearsal transactions with different signer subsets that every owner lands inside the validated signatures. When signing `acceptOwner`, each signer verifies on their device: `to` = the hook address (taken from your own `salt.json`/CREATE2 derivation, not from an explorer or RPC alone), `data` = `0xebbc4965` (`acceptOwner()`), `operation` = Call (never DelegateCall), `value` = 0, `safeTxGas` = `baseGas` = `gasPrice` = 0, `gasToken` = `refundReceiver` = `0x0000…0000`, and `nonce` = the Safe's current nonce (a Safe holding tokens or ETH can be drained through the refund fields of a signed transaction). Keep `salt.json` and the creation tx hash: steps 5 and 7 need them. The audited commit and manifest digest should be recorded in a place the repo does not control (the audit report you hold), not only in this file.

**If launches spam the factory** before your readback: the readback scan is bounded (`SCAN_MAX`, default 300) and batched; above it the solvency scan is skipped, the script prints `PASSED WITH THE SOLVENCY SCAN SKIPPED` and exits 3 unless you raise `SCAN_MAX` (the scan is read-only; raise it as far as your RPC tolerates) or verify solvency with your own monitor and re-run with `ALLOW_SKIP_SCAN=1`. Ownership, code and wiring checks do not depend on the number of launches. If the deployer's target turns out wrong after launches exist, a redeploy leaves the old system live with its `pendingOwner` set: nobody can accept it except that target, so tell nobody to use it.

In steps 4 and 5, the bracketed `[EXPECT_FALLBACK=.. EXPECT_FALLBACK_CODEHASH=..]` pair is included only when the Safe has a fallback handler (omit both otherwise). Rehearsal on a local fork keeps chain id 4663, so the CLI treats it as mainnet and requires every `EXPECT_*` value; use `http://127.0.0.1:8545` and `http://localhost:8545` as RPC and RPC2 (different hostnames).

**Local rehearsal recipe**: start a fork node `npx hardhat node --config hardhat.nolimit.config.js` with `RH_BLOCK=<head-20>` (then send `evm_mine` once, or the first calls at the fork block fail with 'No known hardfork'), point `RH_RPC=http://127.0.0.1:8545` for `deploy.js --network robinhood`, and use `RPC=http://127.0.0.1:8545 RPC2=http://localhost:8545` for `readback.js`. Make sure no other node already listens on that port.

Test coverage note: `test/deploy.realsafe.test.js` and `test/deploy.dryrun.test.js` catch deletion of the Safe hardening, creation-tx and fallback checks, but some ownership-state, wiring and `*_supplied` rows are enforced by the scripts without a dedicated negative test; the CLI enforces the mainnet requirements. `approveHash` rehearsal proves a signer can send a transaction, not that their device can produce an EIP-712 signature: if the final flow is offline signatures, rehearse that flow too.

## PadRouter (swaps and ETH zaps)
`contracts/PadRouter.sol` is the one swap entry point for the pad's $STAG/token pools, plus two zaps through the $STAG curve: `zapBuy` (ETH -> $STAG -> token) and `zapSell` (token -> $STAG -> ETH). It has no owner, no admin, no fee and no upgrade, and it holds nothing between calls. Every call is exact-in with a minimum output and a deadline, and the output goes to the `to` you name (never the router itself). It is separate from the audited core: the manifest and the deployment scripts do not include it, and the core contracts are unchanged.

**Status:** two independent hostile review rounds (two reviewers each, on identical code, commit `717ae83`) found no Critical, High or Medium issues, after a first round whose Low findings were fixed. There is a 33-test fork suite, including the real curve, a mock curve for edge cases, re-entrancy, forced ETH, donated STAG and both currency orderings and modes. This is not a professional audit.

**Deploy:** `new PadRouter(PoolManager, PadHook, STAG, curve)` with `PoolManager = 0x8366a39cc670b4001a1121b8f6a443a643e40951`, `STAG = 0x67Ef4460A1280fBD9d31D6312FEd2Ce1EFd66305`, `curve = 0x8e68043f7553ff7adf30eb8b0baac8d8fc2ed958`, and `PadHook` = the deployed pad hook. The arguments are immutables and are not validated by the constructor, so a wrong one makes a useless (or, for a fake pool manager, hostile-looking) router that still matches the verified source. **Always verify before publishing the address:**

    RPC=<https rpc> ROUTER=<router> HOOK=<hook> node tools/verify-router.js

It checks the four immutables, that the hook pairs the same $STAG and pool manager, and that the runtime equals the local build. Then run a tiny `swapExactIn` and a tiny `zapBuy` from a funded, approved account, and only then put the address in `stagsite/pad/config.js`.

**Known limits (by design):**
- ETH or tokens sent to the router outside a normal call are stuck for good (no sweep: a sweep would be extra attack surface). Nothing a user sends in a call is kept.
- The zaps need the $STAG curve to be live and to pay ETH from the curve address. After the curve graduates, `zapBuy` and `zapSell` revert (funds stay safe) and `swapExactIn` keeps working; the site hides the ETH options then.
- Users approve the router for the exact amount of each trade. Never approve an address the site did not give you: any contract that looks like this router, including one built from the same source with a fake pool manager, could take what you approve to it.
- `zapBuy` sends unspent ETH back to the caller, so a contract caller must be able to receive ETH. A contract recipient of `zapSell` ETH must too, or the call reverts with `SendFailed`.
- A creator burning the war chest can move a pool's price about 1.5% once an hour; keep slippage at 2% or more.

## Wallet-owner mode (one wallet instead of a Safe)
The platform owner can be a single wallet instead of a multisig. This is a deliberate trade. The owner role can only (1) hand ownership over (`setOwner`, then the new owner accepts), (2) do the one-time wiring of the factory and battle contracts (already done by the deployer), and (3) claim the platform's own 3% sell-side share (`claimPlatform(to)`, to any address). It cannot touch liquidity, war chests, creators' fees or holders' money.

What a leaked or phished owner key CAN do: take the share collected so far, and also hand ownership to the attacker (or to a dead address, which freezes the share), who then receives every future platform share, forever. There is no second approver and no revoke. What it cannot do: harm users or pools. A lost key freezes the platform share held in the hook permanently and nothing else (before accept too: the owner stays the function-less PadDeployer and the pending owner never accepts).

Operating rules for a single-key owner:
- Use a hardware wallet. Never sign an EIP-7702 delegation or a smart-account upgrade with this key (readback then fails permanently, and it adds attack surface).
- `claimPlatform(to)` shows only hex on most devices: check `to` on the device screen, and claim to a separate cold address so the owner key only ever needs gas. Keep a little gas ETH on the wallet.
- Rotate with `setOwner(<fresh hardware wallet>)` and accept from it, if you ever doubt the key.
- The owner wallet must have sent a transaction already (a brand-new wallet at nonce 0 is refused): send a 0-value transaction to yourself first.
- Take the HOOK address for the accept transaction from the readback output ("hook has code" row), only after readback has passed with SALT_FILE (it checks the hook against the CREATE2 address derived from salt.json). After accept, run readback again with `EXPECT_OWNER_ACCEPTED=1` and confirm the accept transaction's `from` is your wallet.
- `deploy.js` checks the owner on one RPC only; the dual-RPC readback is the real gate, so a lying single RPC could waste the salt and the deployment before readback fails. Use an RPC you trust for the deploy.
- A used address is not proof you hold its key: keyless presigned-deployment senders and publicly known test keys also have transactions. Only your own hardware wallet screen settles that.
- If your accept transaction fails or reverts (many wallets show only a gas-estimation error), STOP. Nobody owns the hook yet: the PadDeployer is still the owner and a different address is pending. It can also mean you already accepted or used the wrong hook address. Check the hook's `owner()` and `pendingOwner()` on the explorer before doing anything else. Do not publish anything.
- Before accept, readback proves nothing about who holds the key. It prints the owner address in a row marked OWNER WALLET: compare it character by character with your hardware wallet screen. A poisoned address pasted into both `MULTISIG` and `EXPECT_OWNER_EOA` passes every check.

Use it with `OWNER_IS_EOA=1`. It replaces every Safe requirement with these checks (deploy and readback both run them): the owner address has no contract code (a plain wallet; EIP-7702 delegated wallets show code and are refused), it equals `EXPECT_OWNER_EOA` (type it from your wallet app, separately from `MULTISIG`), it is not the throwaway deployer key or any of this system's addresses, PM or STAG, and it has sent at least one transaction (a typo to an unused address is refused). Everything else is unchanged: the pinned build, the manifest digest, the creation-transaction check (the constructor arguments must say `mustBeContract=false`), two RPCs, the salt checks and the ownership/wiring rows.

    # deploy (throwaway key pays gas; MULTISIG is the OWNER WALLET address in this mode)
    OWNER_IS_EOA=1 MULTISIG=<owner wallet> EXPECT_OWNER_EOA=<owner wallet, typed again> EXPECT_MANIFEST_DIGEST=<digest> \
      DEPLOYER_KEY=<throwaway key> SALT_FILE=salt.json npx hardhat run scripts/deploy.js --network robinhood
    # readback before accept
    OWNER_IS_EOA=1 RPC=<rpc1> RPC2=<rpc2> DEPLOYER=<PadDeployer> MULTISIG=<owner wallet> EXPECT_OWNER_EOA=<owner wallet> \
      SALT_FILE=salt.json DEPLOY_TX=<creation tx> EXPECT_MANIFEST_DIGEST=<digest> node scripts/readback.js
    # the owner wallet sends a transaction to the HOOK with data 0xebbc4965 (acceptOwner()), value 0, from the wallet itself
    # readback after accept: the same command plus EXPECT_OWNER_ACCEPTED=1

Steps 0 to 3 of the mainnet section (clean shell and tree, compile, salt) are unchanged. Do not commit the owner wallet address to the repo; pass it as an environment variable.
